# NVRAM for the TP-Link Archer C2300 v1 5GHz radio (BCM4366 on PCIE0).
#
# Board description is from the nvram.nvm captured by Rafal Milecki during his
# original bring-up of this device (OpenWrt commit 8d24da14, "bcm4908: prepare
# to support TP-Link Archer C2300 V1"), which was committed but never wired
# into any image recipe.
#
# The PA calibration here is therefore reference data, not this board's own.
# Every unit's real calibration is per-unit and lives in the "radio_bk" file
# of its "tp_data" partition; the boot scripts read it at
# boot and overrides the values below. These are only the fallback used if
# that partition cannot be read. The same applies to the MAC addresses.
#
# devpath1 MUST be "pcie/1/1/", not "pcie/0/1/" as in the original nvram.nvm.
# brcmfmac computes the value it searches for as
#     domain_nr = pci_domain_nr(bus) + 1;  bus_nr = bus->number;
# (drivers/net/wireless/broadcom/brcm80211/brcmfmac/pcie.c), so for this radio
# at 0000:01:00.0 it looks for "=pcie/1/1" - note the +1 on the domain. With
# the original "pcie/0/1/" the devpath1 block never matched, and the search
# instead hit the second radio's "devpath2=pcie/1/1/" block, feeding this 5GHz
# 3x3 chip the 2.4GHz radio's board description. The firmware then came up as
# "wlc_bmac_attach, deviceid 0x43a1 ... band 2.4G" instead of the correct
# "deviceid 0x43cc ... band 5G". Confirmed on real hardware both ways.
#
# The domain-2 (2.4GHz BCM4360) entries are deliberately not carried over:
# that chip has no mainline Linux driver, and leaving them here would let the
# devpath search match the wrong block again.
